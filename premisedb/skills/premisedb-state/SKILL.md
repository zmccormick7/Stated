# Describe a company's state as of a date

Use this when the session was opened at a cutoff (`PREMISEDB_AS_OF` is set, so every `premisedb` command reads and writes as of that date) and the task names a company, a schema and usually the document that arrived on that date. Use the premisedb-research skill for every command. The schema supplies the fields, their definitions, units and formulas; apply it as written to this company, as you would to any other.

**1. Describe, do not judge.** Every number you record is either quoted from a filing a reader on the cutoff date could see, or computed by a formula from such numbers, so that each can be checked against the filing. A figure the filings do not give is `null` with `basis: undisclosed` and a text saying what was looked for; never estimate it. Write nothing about what the figures mean, nothing from after the cutoff, and nothing you know about the company that the filings you can see do not say. `list --kind Source` shows what you can see; there is nothing to fetch.

**2. Write only what changed.** `list --kind Model --where schema=<schema>` finds the company's Model under the schema, and `expand MODEL_ID --relation in_model` its Variables: the latest version of each key is the state as of the day before. Read the new document and change only the fields it bears on. For each such field, write a Finding that states the new figure and cites the passage, and a new Variable with the same `key` and attributes as the current version and the new `value`, linked `in_model`, `updates` the current version and `depends_on` the Finding. Leave every other field alone: the version in place stays the state, and a field a document does not touch needs no record at all. Never edit an earlier version; a reader at that date must see it as it was, and PremiseDB refuses the edit. Outputs are not yours to compute: `fill-model MODEL_ID` writes a new version of each output whose inputs changed.

**3. The first time, write the whole model.** When the company has no Model under the schema yet, create one, `about` the Entity, with attributes `{"schema": "<schema>"}`, and one Variable per field, `in_model`, with `key`, `value`, `units`, `period` or `periods`, `role` and `basis` (`disclosed`, `derived` or `undisclosed`). Each disclosed input is linked `depends_on` a Finding that states the figure with its period and units and cites the exact passage; each output carries its `formula`, a `null` value and `depends_on` links to every Variable it names. Compose it as one `contribute` payload written to a file with your file-writing tool. Then `fill-model MODEL_ID` stores the outputs, and `check-model MODEL_ID` must report no problems and `exact` true for every output. There is one Model per company and schema, for every date; later sessions add versions to it.

Finish with the Model ID, a table of each key with its value, its stamp and its basis, and the inputs that were undisclosed and why.

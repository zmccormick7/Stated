# Produce a feature's value as of a date

Use this when the session was opened at a cutoff (`PREMISEDB_AS_OF` is set, so every `premisedb` command reads and writes as of that date) and the task names a Feature and a subject. Use the premisedb-research skill for every command. `get FEATURE_ID` shows the Feature: its text is the instructions, and its attributes give the `key` its values carry, the `type` of value (`number`, within `min` and `max` when given; `count`; `boolean`; or one of its `categories`), its `units`, and for a derived feature the `formula`. Apply the instructions as written to this subject, as you would to any other.

**1. Describe, do not predict.** The value is your reading, under the instructions, of the subject's state on the cutoff date, from everything you can see: filings, transcripts, releases and what earlier sessions recorded, across as many documents as bear on it. It need not be a figure any document states. Write nothing about what will happen next, nothing from after the cutoff, and nothing you know about the subject that what you can see does not say. `list --kind Source` and `search` show what you can see; there is nothing to fetch. Follow the instructions on when the value is `null` and when silence in the documents is itself the answer; where they say nothing, the value is `null` only when nothing you can see bears on it. Say in the text what you looked for, and for a value resting on an absence, which documents you read.

**2. Write the value as a Variable.** Find the subject's Entity with `search`. Write one Variable with the Feature's `key`, a `value` of its type (PremiseDB refuses any other), `units` where they apply, `period` labelled as the instructions say, and a text of a sentence or two saying what the reading rests on. Link it `defined_by` the Feature, `about` the Entity, and `depends_on` the Findings it was read from, writing those Findings with citations to the passages where they are not already in the graph. For a derived Feature, give the Variable the Feature's `formula` and a `null` value, link it `depends_on` the latest value about this Entity of each feature the formula names, and run `fill-model VARIABLE_ID`, which computes and stores it.

**3. Start from the latest value.** `list --kind Variable --where key=KEY` shows the feature's earlier values; the latest one `about` this Entity is the reading as of the last date it was made. If your reading is the same, write nothing and say so. If it differs, write the new value as a new Variable as above, linked `updates` the latest one; never edit an earlier value, since a reader at that date must see it as it was, and PremiseDB refuses the edit. Derived features that rest on a changed value are not yours to redo: `fill-model ENTITY_ID` writes their new versions.

Finish with the Variable's ID, its value and what it rests on, or why it is null or unchanged.

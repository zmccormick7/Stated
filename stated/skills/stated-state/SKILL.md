# Produce a feature's value as of a date

Use this when the session was opened at a cutoff (`STATED_AS_OF` is set, so every `stated` command reads and writes as of that date) and the task names a feature and a subject. Use the stated-research skill for every command. `feature KEY` shows the feature's definition: its `instructions`, its `id`, the `key` its values carry, the `type` of value (`number`, within `min` and `max` when given; `count`; `boolean`; or one of its `categories`), its `units`. A derived feature, one with a `formula`, is not written by a session: Stated computes it from its inputs. Apply the instructions as written to this subject, as you would to any other.

**1. Describe, do not predict.** The value is your reading, under the instructions, of the subject's state on the cutoff date, from everything you can see: filings, transcripts, releases and what earlier sessions recorded, across as many documents as bear on it. It need not be a figure any document states. Write nothing about what will happen next, nothing from after the cutoff, and nothing you know about the subject that what you can see does not say. `list --kind Source` and `search` show what you can see; there is nothing to fetch. Follow the instructions on when the value is `null` and when silence in the documents is itself the answer; where they say nothing, the value is `null` only when nothing you can see bears on it. Say in the text what you looked for, and for a value resting on an absence, which documents you read.

**2. Write the value as a Variable.** Find the subject's Entity with `search`. Write one Variable with the feature's `key`, `feature` set to the definition's `id`, a `value` of its type (Stated refuses any other), `units` where they apply, `period` labelled as the instructions say, and a text of a sentence or two saying what the reading rests on. Link it `about` the Entity and `depends_on` the Findings it was read from, writing those Findings with citations to the passages where they are not already in the graph. If the instructions make the answer depend on how old the evidence is, such as a document that counts only if filed within some period, set `expires` to the first date on which your reading would no longer hold if nothing new were published, the day the evidence it rests on ages out; otherwise leave it out. `run-features` reads the value again on that date.

**3. Start from the latest value.** `list --kind Variable --where feature=DEFINITION_ID` shows this feature's earlier values, made under this definition; the latest one `about` this Entity is the reading as of the last date it was made. Variables that only share the key, such as a driver model's, are not its values. If your reading is the same, do not write it again: run `confirm VALUE_ID --input FILE` with your `author_id` on that latest value, which records that it still held on this date, and say so; give `expires` in the same way when the reading would lapse with no new document. If it differs, write the new value as a new Variable as above, linked `updates` the latest one; never edit an earlier value, since a reader at that date must see it as it was, and Stated refuses the edit. Derived features that rest on a changed value are not yours to redo: `run-features` computes them after the sessions, or `derive-features --subject ENTITY_ID`.

Finish with the Variable's ID, its value and what it rests on, or why it is null or unchanged.
